## Specification decisions and material conflicts

1. **Local implementation versus hosted prerequisite.** Point puts hosted Postgres before the full deployed rehearsal; the current request explicitly excludes deployment. The source supports `pg` for production and uses PGlite's real Postgres transactions locally. All local tests use the actual SQL engine, not an in-memory JavaScript mock. Recommendation: complete the same rehearsal against external Postgres/HTTPS before declaring live readiness. No claim is made that local verification completes T-010–T-012.
2. **Private identity versus named portrait files.** Existing portrait filenames disclose role-card names. Assets are preserved byte-for-byte and served through neutral `/portraits/1.png`–`7.png` routes for the private card. Public profile pictures use seven generic `/avatars/0.svg`–`6.svg` styles. Source documents and original named asset routes are not public.
3. **Code-free onboarding and private details.** The latest operator direction retains seven paper profiles and replaces host-issued codes with joining through the room QR/link. The first modal collects the paper name and home town privately, public in-character bio, picture and banner. The reusable `identifyProfileByName` function matches a unique first name, surname or full name case- and accent-insensitively (including ø/o, æ/ae and ö/o). Ambiguous or conflicting names are not assigned. Preview, joining and profile edits share this matcher. The preview updates as the user types; Personal info and Profile tabs separate details from appearance. The server claims that role atomically, and assigns its anonymous username. Public API projections never include the private details; only the posting credential can retrieve them. The host-controlled exposure still discloses the role identity as part of the exercise. Existing sessions receive anonymous username fallbacks without discarding their posts or credentials. Reconcile the older Point code requirement before the release freeze.
4. **Required joining.** The latest operator direction removes observer entry. Setup cannot be dismissed without joining; feed and profile endpoints require a participant/viewer credential or authenticated host. New joins close at launch. Existing teams can reconnect and explicitly share a scoped read-only team link. The public projector remains limited to QR, prompts and aggregate counts.
5. **Expiry versus implicit background work.** The user has not authorized an external scheduled cleanup service. Deadlines immediately deny access; expiry cleanup is performed on session access or host session listing. Explicit host clearing is the recommended end-of-event operation. Recommendation: if exact unattended physical deletion is required, separately configure and test an authorized cleanup job and provider backup retention policy.
6. **Proposed relational tables versus small session aggregate.** The plan labels its tables as design proposals. This implementation stores a bounded seven-team session in one JSONB aggregate protected by `SELECT ... FOR UPDATE`, plus a host-cookie revocation table. Claims, post retries, flags, targets, waves and phase changes share the same transaction. This keeps concurrent Node instances consistent with a small migration surface. Recommendation: normalize only if the app grows beyond the bounded workshop scope; cap is 2,000 posts per session.
7. **Original prototype contracts.** Random public full-name identities, unlimited browser claims, default password and restart-clears-everything behavior conflict with the agreed privacy and persistence requirements. Those tests were replaced with the new contracts. Existing prototype UI source and third-party notices are retained but obsolete entry points are not served.
